# 영속 업무 큐 운영 계약

사용자의 원 지시, 실행 티켓, 모델 실행 시도와 검증 결과를 구분합니다.
표시 이름은 내부 ID·owner·계정 binding을 바꾸지 않습니다. 기존 제품 팀과 준비 세션을 그대로 두고 공통 부서는 `operations.departments`에 명시합니다.

## 접수와 승인

`queue intake --ticket-file <원문> --key <원 지시 키>`는 원문을 영속 저장합니다. 등록 자체는 실행 승인이 아닙니다.
설정한 Codex 총괄의 원문 저널은 소비기가 읽기 전용으로 관측합니다. 첫 관측 이전의 과거 대화를 재접수하지 않으며, 재시작 후에는 저장된 위치부터 이어 읽습니다. 관측 범위 밖 대화는 이 방법으로 수집되지 않습니다.
설치된 저널 계약에 맞춰 기본 `response_item`의 사용자 입력을 읽으며, 다른 형식은 명시 설정으로만 선택합니다. 총괄에게 보낸 자동 분류 요청은 다시 접수하지 않습니다.

기존 총괄의 실제 owner·PID·모델·입력·한도와 공통 용량이 확인되면 원 지시별 분류 요청을 한 번 전달합니다. intent를 먼저 저장하며 수신 불명은 재전송하지 않습니다. 총괄은 전달받은 정확한 `queue classify` 명령으로 분류안을 제출합니다. 새 root는 승인 대기이며, 같은 원 지시에 연결된 부모의 축소 하위 작업만 기존 승인을 사용합니다. 모호한 지시는 구체적인 확인 대기로 표시합니다.

운영본부는 목표·담당 제품·역할·완료 조건·검증 argv·경로·데이터·계정 정책을 명시한 티켓을 등록합니다.
`queue create --ticket-file <계약> --key <중복 방지 키>`는 기본적으로 승인 대기입니다. 사용자의 실제 승인 근거가 있을 때만 `--user-approved`를 사용합니다. 후속 명시 승인은 `queue approve`가 티켓·계약·범위 digest를 대조합니다.

부모의 승인 파일 digest는 자식에게 그대로 전달합니다. 파일이 바뀌면 자동 실행하지 않습니다.
필수 하위 작업과 결함 수정은 제품·데이터·계정·경로·자원·실행 정책이 축소되고 검증 명령이 유지될 때만 승인 범위 안에서 실행합니다. 호스트가 생성한 독립 리뷰 검증 명령은 제출물과 소스 digest에 고정됩니다. 추가 개선은 backlog이며 별도 승인이 필요합니다.

## 실행과 완료

소비기는 승인·의존성·실제 세션·입력 상태·계정·사용량·전역 용량·충돌 자원을 확인합니다.
SQLite 트랜잭션 안에서 실행 시도와 자원 예약을 먼저 기록합니다. 그 뒤 기존 역할 정책에 맞는 세션을 사용하거나 기존 native launcher로 빈 역할 세션을 엽니다. 외부 전달 결과가 불명이면 같은 시도를 다시 보내지 않습니다.

실행자는 전달된 정확한 `queue receipt`를 먼저 실행하고 결과 파일을 `queue submit`으로 제출합니다.
수신·턴 종료·제출은 업무 완료가 아닙니다. 호스트가 실제 PID·owner·시도·idle과 쓰기 중단을 대조한 뒤 승인된 검증 명령을 실행합니다. 코드·통합은 기존 workflow 승인과 현재 HEAD·소스 fingerprint, 별도 실행자의 독립 리뷰를 추가로 요구합니다.

검증 실패나 리뷰 반려는 원 시도에 연결된 수정 티켓을 생성합니다. 필수 자식이 남아 있으면 부모는 완료하지 않습니다.
부모의 실행 슬롯 반환과 쓰기 lease 해제는 별도입니다. 보유한 쓰기 lease는 동일한 실제 idle 실행자에게만 원자적으로 이어 주며, 다른 실행자에게 넘기려면 중단된 쓰기 근거가 필요합니다.

## 용량과 관측 경계

네 계정 프로필, 준비 후보 수, 실제 실행 용량은 독립적입니다.
`operations.resource_policy`의 `global_limit` 기본값은 3이며, profile별 제한과 관측 유효기간을 따로 둡니다. 같은 팀 대신 겹치는 경로·worktree·통합 브랜치·기기 등을 명시 자원으로 예약합니다.
장부 예약과 HC에서 관측한 모델 턴을 합산합니다. HC 밖 모델 실행은 전체 통제 범위에 포함되지 않습니다. 관측 실패는 여유 슬롯 0 또는 성공으로 위장하지 않습니다.
HC 관측의 단위는 터미널 foreground 모델 프로세스의 상태입니다. 같은 프로세스 안의 하위 에이전트와 API 모델 호출은 별도 집계하지 못합니다. 직접 시작한 모델은 관측해 합산하지만 배정을 사전에 통제하지 못합니다.

원 지시별 티켓 수·실행 횟수·토큰 예약 예산을 확인합니다. 토큰 실측이 없는 제출은 예약을 유지하며 비용 0으로 처리하지 않습니다. 이 예산은 호스트의 예약 한도이며 모델 공급자의 실제 토큰 상한을 강제로 보장하지 않습니다.
UI 티켓은 일반 워커 실행에서 차단합니다. 기존 UI 검증실의 개인 Codex·실행 머신·화면 독점·권한 계약을 별도로 유지합니다.
`operations.ui_lab`의 명시된 공식 CLI와 실제 워커 binding이 준비되면 전용 어댑터가 동일 티켓·시도에 고정된 요청 ID로 연결합니다. UI 접수·실제 claim·passed를 구분하고, 대상 버전·체크·근거 파일·owner·실제 idle과 쓰기 중단을 대조한 뒤에만 종결합니다. 전달·조회 불명은 기존 요청을 대조하며 새 요청을 만들지 않습니다. 호스트 잠금·권한 등의 사전 차단 이유가 있으면 전달하지 않습니다. 어댑터 밖 UI 업무와 물리 화면 사용자는 통제 범위 밖입니다.

## 상시 소비와 복구

`service install`은 launchd guardian 정의를 저장합니다. 운영자가 현재 도움말에 맞는 launchd 명령으로 로드하면 guardian은 기존 `auto-context serve`의 단일 실행 경로를 사용합니다.
티켓·제출·반환 이벤트는 로컬 wake 신호를 보내고, 신호 유실에는 최대 5초 주기 대조를 사용합니다. 이는 배정 지연의 설계 목표이며 실제 계정 조회·모델 기동 지연은 따로 측정해야 합니다.
배정은 같은 supervisor PID와 lifetime 잠금 안의 별도 thread에서 처리합니다. 인계 관측이 막혀도 별도 wake 채널로 깨어나며 독립 heartbeat·최근 성공·오류를 기록합니다. 소스 변경과 종료 시 새 tick을 막고 현재 tick을 정리한 뒤 잠금을 반환합니다.
살아 있지만 heartbeat가 늦은 소비기나 결과 불명 실행자는 시간만으로 종료·재실행하지 않습니다.

과거 `done/received` 요청의 세션 재개는 `pool rebind-receiver`가 원문 SHA, 이전 터미널 종료, 같은 owner·시도·native session, ledger 재개 사건과 현재 PID·idle을 대조합니다. 원문 바이트와 진단 이력을 보존하며 종결·전송은 수행하지 않습니다. 과거 uncertain은 이 경로로 해제하지 않습니다.

## 적용과 검증

운영 전에는 SQLite backup API로 DB를 백업하고 config·pool·coordinator·mod·binding을 보존합니다.
새 테이블은 기존 task 상태를 덮어쓰지 않는 추가 마이그레이션입니다. 복구 시 진행 중 작업을 먼저 대조하고 소비기만 안전하게 멈춘 뒤 이전 소스와 설정으로 돌아갑니다. 적용 이후 생긴 티켓을 옛 DB로 덮어쓰면 안 됩니다.

호스트 대역 검사는 실제 SQLite·파일·검증 명령을 쓰되 HC와 계정/모델 경계를 바꿉니다. 이 검사는 실제 모델 처리·UI 렌더링·launchd 재부팅 복구를 증명하지 않습니다. 운영 보고에는 그 경계와 미실행 항목을 따로 기록합니다.
